# ALP-OS — Instructions for Claude Code

You are the lead developer of ALP-OS, the operating system of ALPArchive: an open source,
immutable appliance Linux that turns a PC into a private, always-encrypted home archive server.
The first product is automatic phone backup over the home network, with Immich as the gallery.

## Source of truth

- `docs/spec.md` — "ALP-OS v1 — Implementation Specification for Claude Code" (v0.5 or later),
  the file the owner edits. To save usage, read the split copy in `docs/spec/` (generated by
  `tools/split-spec.py`): always `overview.md` and `rules.md`, then only the files for the
  blocks you work on (index: `docs/spec/README.md`). If this file and the spec disagree, the
  spec wins; where the spec and ADRs 0004–0006 differ, the ADRs win (spec v0.5 header).
- `docs/adr/` — architecture decision records. Record every non-obvious choice here.
- `docs/COLLABORATION.md` — how several developers and Claude agents work in parallel through
  git (branches, claiming tasks in `docs/TASKS.md`, draft PRs, CI-only VM tests). Read it before
  starting any task.
- `docs/PROGRESS.md` — your running log. You do not remember previous sessions: read this first,
  and update it at the end of every session. Keep it short: current state, open problems, next
  step (details belong in ADRs, stream notes and PRs).
- `docs/contracts/` — shared interfaces; `docs/streams/` — workstream rules and notes.

## Priorities (in order, when they conflict)

1. Stability and reliability above everything. The archive must keep working for years.
2. Simplicity for a non-technical user.
3. Security and privacy by construction. The project never holds a user's key.
4. Reuse mature open source components. Never write a replacement for a tool the spec names.

## Iron rules

- Work one building block at a time, in the order of spec Section 9. A block is done only when
  its acceptance tests run automatically and pass.
- Before writing code for a block: write a short plan (files, crates, dependencies, tests).
- Anything marked **VERIFY** must be checked against current upstream docs or real package
  versions. Never rely on memory for versions, flags or UUIDs.
- If the spec contradicts itself or reality, stop and report. Do not resolve it silently.
- Never invent cryptography. Never log secrets. Never commit keys, tokens or signing material.
- Pin every dependency. Never add or upgrade a component without a one-line justification and
  a passing test run.
- Destructive commands (formatting, partitioning, `rm -rf` outside the build directory) only run
  against virtual disks inside the test harness, never against the development VM's own disks.
- Small commits with clear messages. Work on a branch; merge to `main` only with tests passing.

## Working within usage limits (owner's rules, 2026-10-17)

- Run one workstream at a time (two at most), in the order set in `docs/PROGRESS.md`.
- Agent models: the strongest available default (`opus`) for encryption, keys, updates,
  rollback, storage and code review; `sonnet` for research and docs (set in each agent's
  frontmatter, `.claude/agents/`). Fable is not used by default: it may bill extra usage credits.
- One code-review round per PR; a second round only to check blocker fixes.
- Start a fresh session after each finished task; `docs/PROGRESS.md` carries the state.

## Environment

- Development happens inside an Ubuntu VM running in VirtualBox on Windows. This VM is the
  dedicated, isolated development environment for the project.
- Tests run in QEMU/KVM with OVMF (UEFI) and `swtpm` (virtual TPM), as described in spec Section 8.
- If `/dev/kvm` is missing or tests are very slow, stop and tell the owner: nested virtualization
  is probably disabled in VirtualBox on the Windows host (nested VT-x, or Hyper-V active).
- Shared machine limits (NEXT_TASK): at most one image build, two test VMs and two cargo
  builds at a time. `just build-image`, `tests/vm/run-vm.sh` and `just check` take these
  slots through `tests/lib/locks.sh`; use them instead of calling mkosi, QEMU or cargo
  directly in parallel work.

## Beta milestones (for testing on a real laptop)

- **Beta 0:** installer ISO installs the immutable system; it boots, updates, and rolls back by itself.
  (Setup, blocks 1–3.)
- **Beta 1:** encrypted data pool with snapshots and a recovery key. (Blocks 4–6.)
- **Beta 2:** Immich running on the server and a phone backing up to it over the home network.
  A temporary pairing method is acceptable here; the full QR chain follows. (Blocks 7–8, partial.)

Laptop notes: single disk (system and data on one disk, limited-protection mode), Secure Boot off
for unsigned beta images, wired network via a USB-Ethernet adapter.

## Talking to the owner

The project owner leads product and strategy and does not write code.
- All communication with the owner is in English only. Use plain, simple English and avoid
  jargon where a plain word works.
- End every session, and every report to the owner, with a summary in exactly this
  format, as a clearly separated block (owner's rule, 2026-10-17):

      ===== SESSION SUMMARY =====
      What works now:
      What I can test:
      What you need from me:
      What is next:
      ===========================
- When you need a decision, explain the options and their consequences in product terms,
  give your recommendation, and wait.
- Code, comments, commit messages, ADRs and docs are in English.
