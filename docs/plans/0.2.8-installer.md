# 0.2.8 installer plan (block 7, stream D)

Source: spec block 7, block 4, ADR 0028 (wins over the spec where they differ),
contracts `disk-layout.md` and `firstboot-seed.md`. This plan covers disk
discovery, operating-system detection, the two start paths and the pool plan.
The native screen (GTK 4) has its own plan.

## (a) Disk discovery: every disk, with a role or a reason

- Every `type: disk` device is listed: internal SATA/NVMe, USB disks and
  sticks, SD cards (built-in reader `mmcblk*` or USB reader). Not listed:
  `loop`, `zram`, `ram`, `nbd`, `md`/`dm` top-level devices, CD drives
  (`type: rom`); they are not connected disks.
- Shown for each: model (or "Unknown disk"), size (decimal GB/TB, as disk
  makers count), connection (internal, USB, SD card, NVMe ...).
- Each disk gets exactly one verdict:
  - **Usable** with the roles it can take: *system and data* (single disk,
    >= 64 GB, internal), *system only* (>= 32 GB, internal), *data*
    (internal or USB, >= the data minimum). Plus what is on it now:
    *empty* or *holds files* (with file system names and labels) so the
    confirm screen can say exactly what will be erased. "Internal" means
    not USB, not a memory card (SD/eMMC) and not removable; memory cards
    and USB disks can only be data disks.
  - **Not usable** with one plain reason, first match wins:
    1. the USB stick ALP-OS started from;
    2. in use right now (something on it is mounted);
    3. no card or medium inserted (size 0);
    4. read-only (for example an SD card with its lock switch on);
    5. holds an operating system (see (b));
    6. part of a disk group another system uses (RAID, LVM, ZFS, Windows
       Storage Spaces or dynamic disks, Apple RAID);
    7. already holds an ALP-OS archive (partition label `alp-data`;
       opening an existing archive is a later version; never erased);
    8. holds encrypted data ALP-OS cannot look inside (LUKS);
    9. too small (shows the size and the size needed);
    10. a USB or removable disk while the start stick could not be found
        (fail closed, as Live does since review 0.2.5).
- Reasons have a stable key (`holds_windows`, `boot_stick`, ...) for the
  translation files (spec 2.2) and an English fallback text.

## (b) Operating-system detection (greyed out, never selectable in 0.2.8)

Evidence comes from GPT partition type GUIDs, MBR type bytes and flags,
partition labels and file system names (`FSTYPE`). Any one is enough.

| Finding | Evidence |
|---|---|
| ALP-OS system | partition label `alp-state`, or a root partition labelled `alp-os_*` (disk-layout contract) |
| Windows | Microsoft reserved `E3C9E316-0B5C-4DB8-817D-F92DF00215AE`, Windows recovery `DE94BBA4-06D1-4D40-A16A-BFD50179D6AC`, fs `BitLocker` or `ReFS`; MBR `0x27`; NTFS on a disk that also has an EFI or Microsoft reserved partition; NTFS with the MBR boot flag `0x80` |
| macOS | APFS `7C3457EF-0000-11AA-AA11-00306543ECAC`, HFS+ `48465300-0000-11AA-AA11-00306543ECAC`, Apple boot `426F6F74-...`, Apple Core storage `53746F72-...`, Apple Silicon boot/recovery; fs `apfs`, `hfsplus`, `cs_fvault2`; MBR `0xab`, `0xaf` |
| Linux | root, `/usr` and their verity types for x86, x86-64, ARM, ARM-64 and RISC-V-64 (from the libfdisk table), Linux extended boot `BC13C2FF-...`, swap `0657FD6D-...`, home, server data, variable data, temporary data, user home; fs `swap`/`swsuspend`; BIOS boot `21686148-6449-6E6F-744E-656564454649`; MBR `0x82`, or `0x83` with the boot flag |
| ChromeOS, BSD, Solaris, other systems | their kernel/root/boot types from the libfdisk table (ChromeOS kernel/root, FreeBSD/NetBSD/OpenBSD/MidnightBSD/DragonFly, Solaris, Haiku, QNX, ...) |
| Unknown system | EFI system partition `C12A7328-F81F-11D2-BA4B-00A0C93EC93B` or MBR `0xef` with nothing more specific; any other MBR partition with the boot flag; `iso9660`/`udf` (a start stick or disc image of another system) |

Rules and limits:

- **Any ESP counts as "holds a system".** The ADR says "ESP with a boot
  loader"; looking for the loader means mounting the ESP. 0.2.8 does not
  mount anything, so an ESP alone is enough (fails safe: an empty ESP on an
  otherwise blank disk is greyed out too). A later version may mount it
  read-only to look for `EFI/*/*.efi`.
- **Known gap:** a Linux root on a plain "Linux filesystem" partition with
  its boot partition on another disk (or a legacy MBR install without the
  boot flag) looks like a data disk. It is then shown as *holds files* and
  needs the strong confirmation; it is not silently erased. Closing the
  gap means mounting read-only and looking for `/etc/os-release` (later).
- A plain NTFS/exFAT/FAT USB disk with no ESP/MSR/boot flag is a data disk
  (*holds files*), not Windows.
- Also counted as a system: fs `erofs`, `squashfs`, `DM_verity_hash`
  (read-only system images, Linux), and a FAT partition labelled `boot`,
  `bootfs`, `system-boot` or `EFI` (for example a Raspberry Pi card, which
  uses MBR without a boot flag).
- All 71 GUIDs in the code were checked by a script against the libfdisk
  2.39.3 table (names and values); the MBR bytes against its `dos` table.
- **The start stick is never offered:** the caller passes the kernel name
  of the disk ALP-OS runs from (`alp_hw::inspect` follows the root file
  system through dm-verity to its disk, as Live does). As a second guard,
  any disk with a mounted partition or holder is refused as "in use". If
  the start disk was not found, every USB or removable disk is refused.
- The verdict is computed again right before anything is written, and the
  write is refused if the disk, its size or its partitions changed since the
  user confirmed (spec block 7: never touch an unconfirmed disk;
  `alp_hw::safety::check_member` runs again in `alp-storage`).

## (c) Two paths

1. **Install on this computer.** The system goes on one internal disk
   (not USB, not removable). One disk: system plus `alp-data` on it
   (>= 64 GB; protection `dup`). More disks: system on the smallest
   suitable internal disk, `alp-data` partitions on the chosen data disks
   (`image/install-layout/data-disk/`); the system disk does not join the
   pool unless it is the only disk. Then remove the stick and restart.
2. **Keep running from the USB stick.** Nothing is installed; the stick
   stays the system disk and the chosen data disks (internal or USB) get an
   `alp-data` partition each. **Open (stream A):** the stick needs a state
   partition and updates in place (ADR 0026 layout); confirm this layout is
   what the 0.2.8 stick image has.

Both paths show the same disk list and the same confirm step (typed word or
press-and-hold, spec block 7), naming every disk that will be erased and
what is on it now.

## (d) Pool plan

- One data disk: Btrfs `dup` for data and metadata; the screen shows half
  the capacity and says it protects against damaged files, not against a
  dead disk. Two or more: `RAID1` for data and metadata. `RAID1c3` and
  `RAID10` only by explicit choice; `single` only by the advanced setting.
  RAID5/6 cannot be expressed (`alp_hw::RaidProfile` has no such variant).
- Usable capacity, RAID1 with different sizes: `min(total / 2, total -
  largest)`; dup: `size / 2` (minus metadata overhead; **VERIFY** against
  `btrfs filesystem usage` on the trixie btrfs-progs in the VM test).
- Members by GPT partition UUID (`PoolMember::ExistingPartition`), one LUKS2
  container per disk, all with the pool key (block 4, unchanged).
- **Room for the later "local backup disk" role:** a backup disk is never a
  pool member, and adding the role adds a job, not a pool layout change.
  **Owner rule (0.2.7 test note 2, 2026-11-24), installed system only:** a
  USB backup disk is exFAT. NTFS is never offered; the default and only
  format choice is exFAT (with the slide when the disk holds files). An
  ext4 volume with no files is used as it is. Live keeps accepting exFAT,
  NTFS and ext4. The rule is `alp_live::archive::installed_backup_disk`.
  The copy on the disk stays encrypted (the archive file as on Live), so
  exFAT changes where it can be read, not who can read it. This replaces the
  earlier idea of a LUKS2 + Btrfs backup disk fed by `btrfs send`; how
  snapshots of `@archive` reach the exFAT disk is decided when the role is
  built.

## (e) Built for tens of terabytes

- All sizes are `u64` bytes; display in decimal TB. Tests use 20 TB disks
  and a 6-disk RAID1 capacity case.
- Always GPT (MBR cannot address more than 2 TiB). 4K-sector disks: repart
  handles alignment (**VERIFY** in the 2-disk VM test with a 4Kn virtual
  disk, `logical_block_size=4096`).
- Discovery reads no file data and does not wake sleeping disks except the
  targeted `blkid -p`; the list is small whatever the archive size.
- Scrub and balance on tens of TB take many hours: throttled, resumable
  across reboots, shown with an estimate (block 4). First pool creation does
  not pre-write the disks (no full-disk wipe; LUKS2 `--integrity` is not
  used, so no initial pass) — **VERIFY** in stream B's plan.

## Install plan (step 2, `crates/alp-installer/src/plan.rs`)

- Input: the discovery (`blockdev::discover`) and the user's `Choice`:
  `InstallTo { system_disk }` or `KeepRunning`, the data disks, and the
  profile (`Auto`, or `Explicit` for `single` on one disk, `raid1c3` on
  three or more, `raid10` on four or more; RAID5/6 cannot be written).
- Output, in order: `Partition` (disk + repart definition sets
  `system`, `single-disk-data`, `data-disk` from `image/install-layout/`),
  `CopySystem` (install path only), `UseExistingState` (keep-running
  only), `WriteSeed` (members, data and metadata profile). Plus the erase
  list (disk, model, size, what is on it) and the pool sketch (members,
  profiles, estimated usable bytes, protection).
- Refusals (`ALP-INST-402`): any disk not usable for its role (verdict
  from `blockdev`), the start stick, a disk named twice, the system disk
  also chosen as a data disk, keep-running without a found start stick or
  without its `alp-state` partition, a profile that does not fit.
- Re-check (`ALP-INST-401`): `InstallPlan::recheck` takes a fresh
  discovery right before writing and refuses if **anything** differs
  (any disk added or removed, size, model, connection, partitions,
  contents, mounts, verdict), then plans again and requires the same plan.
  Strict on purpose: plugging in an unrelated stick between Confirm and
  Install sends the user back to choose again; that is rare and safe.
  Kernel names alone cannot tell two identical blank disks apart after a
  re-plug; the first-boot seed then checks serials (`firstboot-seed.md`
  rule 2), and the executor must also compare by-id names (next step).
- Capacity (`crates/alp-installer/src/capacity.rs`): data partition =
  disk - system area (19.25 GiB on a single disk) - GPT overhead
  (4 MiB) - LUKS2 header (16 MiB, **VERIFY** stream B's luksFormat
  default). Usable: `dup` half, `single` all, `c` copies on different
  disks: `total / c` if no disk is larger than that, otherwise drop the
  largest and repeat with `c - 1` (RAID1: `min(total/2, total - largest)`).
  RAID10 uses the RAID1 figure (**VERIFY**). Estimates; Btrfs metadata is
  not subtracted (**VERIFY** against `btrfs filesystem usage`). When
  stream B writes `BtrfsBackend::plan_pool`, the function moves there.
- Data disk minimum 32 GB (owner, 2026-11-24): the constant
  `plan::MIN_DATA_DISK_BYTES`, because `profile.rs` is a contract and a
  stream PR may not change it (stream rule 3). Contract change request in
  `docs/streams/d-installer.md`; the lead can make it a `contract:` PR.

## Executor (step 3, `crates/alp-installer/src/exec.rs`)

- Runs every program through one `Runner` trait (`run.rs`: program, fixed
  argument list, optional stdin; status, stdout, stderr). Unit tests use a
  recording mock and assert the exact command list; nothing touches a disk.
- **Preflight, before any write:** the seed must be buildable (see
  "Not ready" below); a fresh `lsblk` discovery must pass
  `InstallPlan::recheck`; every disk the plan uses (erase list, plus the
  stick on the keep-running path) must have the same by-id name, serial
  and size as at confirmation (`lsblk --json --bytes --nodeps --output
  NAME,ID-LINK,SERIAL,SIZE`; JSON key `id-link` checked on 2.39.3). A disk
  without a by-id name is refused (`ALP-INST-403`).
- **Device guard:** a device path is built only for a disk in the erase
  list; anything else stops with `ALP-INST-408`. The seed's mount uses
  `/dev/disk/by-partuuid/<uuid>` of the `alp-state` just read back from a
  partitioned disk.
- **Steps and commands** (fixed lists, built from the plan):
  - Partition: `systemd-repart --dry-run=no --no-pager --empty=force
    --seed=random --definitions=<layout>/<set>... /dev/<disk>`, then
    `udevadm settle --timeout=30`, then `lsblk --json --output
    NAME,PARTUUID,PARTLABEL /dev/<disk>`; the labels must equal the
    definition sets' labels in order and every partition UUID must be new
    and unique across disks (`ALP-INST-404`).
  - Copy system: `/usr/lib/systemd/systemd-sysupdate
    --definitions=<install-time defs> --image=/dev/<disk> update`, then
    `bootctl --image=/dev/<disk> install` (`ALP-INST-405`).
  - Keep-running: the stick's `alp-state` must be the mounted partition
    from the plan; no command.
  - Seed: build `alp_core::firstboot::FirstbootSeed` (members by by-id,
    serial, size, `alp-data` partition UUID; plan digest over the
    `PoolPlan` with those members), TOML (`seed.rs`); install path:
    `mkdir -p`, `mount -t ext4`, `install -m 0600 /dev/stdin
    <mnt>/firstboot-seed.toml`, `sync -f`, `umount` (always tried);
    keep-running: `install` and `sync` into `/var/lib/alp`
    (`ALP-INST-406`).
- Progress: `step` (0 = preflight), `steps`, `percent`, translation key,
  plain message; 100 at the end.
- Failure: stops at once with the code and the step number; later steps
  never run. Disks outside the plan are never named in any command.
- **Who creates the pool:** first boot (stream B, `create_pool` from the
  seed), as `firstboot-seed.md` says; the executor runs no `cryptsetup`,
  `mkfs` or `btrfs` (spec rule 6 keeps those in `alp-storage`).
- **Plan digest:** `PlanDigest for PoolPlan` is implemented in `alp-hw`
  (SHA3-256 over a versioned, length-prefixed encoding; members sorted,
  partition UUIDs lower-cased; frozen by a golden test cross-checked with
  Python's `hashlib`). `ContractDigest::ready()` is true. `ALP-INST-407`
  stays as a guard for a future digest that is not ready.
- Paths on the installer image (stream A must ship them):
  `/usr/bin/alp-installer`, `/usr/lib/alp/install-layout/` (copy of
  `image/install-layout/`), and the image must not run
  Live's disk protection (`alp-live-protect`), which makes other disks
  read-only. Copying the system (spike done, 2026-11-25): slot 1 and its
  verity are filled by systemd-repart `CopyBlocks=auto` during partitioning
  (sysupdate's `partition` resource is target-only, sysupdate.d(5) v257);
  then `bootctl install` and the running UKI copied from the stick's ESP
  (contract `disk-layout.md`).
- `src/main.rs` is a scripted front end for the VM tests:
  `alp-installer list | install --system <d> [--data <d>]... --confirm-erase
  <d,...> | keep-running --data <d>... --confirm-erase <d,...>`;
  `--confirm-erase` must name exactly the plan's erase list.

### Executor VERIFY items

Flags already used in the repo: `--dry-run=no`, `--no-pager`,
`--definitions=` (several allowed, `check-install-layout.sh`),
`udevadm settle --timeout=30`, `lsblk --json --output`, `mount`, `umount`,
`sync -f`. Not yet used in the repo, so **VERIFY** against trixie's

- `systemd-repart --empty=force` (listed in systemd 255 `--help`; needed so
  repart replaces an existing partition table instead of adding to it).
- `systemd-repart --seed=random` (systemd 255 `--help` lists `--seed=UUID`;
  the value `random` must be checked). Without a random seed, two disks
  partitioned by the same installer could get the same partition UUIDs;
  the executor refuses that case after read-back either way.
- Whether repart wipes old file system signatures at the start of new
  partitions (otherwise an old NTFS or ext4 header could still be found).
- `systemd-sysupdate --definitions= --image= update` and the install-time
  transfer definitions (stream A + D spike; the source is the running
  stick's own image).
- `bootctl --image= install`.
- `install -m 0600 /dev/stdin <file>` (GNU coreutils), and the seed's owner
  (contract: owner alpd; the installer image has no alpd user, first boot
  may need to chown).
- `lsblk --nodeps` and `ID-LINK` on util-linux 2.41.
- QEMU `virtio-blk-pci,serial=` (T-INST-01 gives the virtual disks by-id
  names this way).
