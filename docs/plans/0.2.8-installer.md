# 0.2.8 installer plan (block 7, stream D)

Source: spec block 7, block 4, ADR 0028 (wins over the spec where they differ),
contracts `disk-layout.md` and `firstboot-seed.md`. This plan covers disk
discovery, operating-system detection, the two start paths and the pool plan.
The native screen (GTK 4) has its own plan.

  util-linux **2.39.3** `libfdisk.so.1` on the dev machine (read through its

- **blkid has no JSON output** (2.39.3 `--output` is value, device, export

- **VERIFY:** `lsblk` does not wake sleeping disks (it reads udev and

## (a) Disk discovery: every disk, with a role or a reason

- Every `type: disk` device is listed: internal SATA/NVMe, USB disks and
  sticks, SD cards (built-in reader `mmcblk*` or USB reader). Not listed:
  `loop`, `zram`, `ram`, `nbd`, `md`/`dm` top-level devices, CD drives
  (`type: rom`); they are not connected disks.
- Shown for each: model (or "Unknown disk"), size (decimal GB/TB, as disk
  makers count), connection (internal, USB, SD card, NVMe ...).
- Each disk gets exactly one verdict:
  - **Usable** with the roles it can take: *system and data* (single disk,
    >= 64 GB, internal), *system only* (>= 32 GB, internal), *data*
    (internal or USB, >= the data minimum). Plus what is on it now:
    *empty* or *holds files* (with file system names and labels) so the
    confirm screen can say exactly what will be erased. "Internal" means
    not USB, not a memory card (SD/eMMC) and not removable; memory cards
    and USB disks can only be data disks.
  - **Not usable** with one plain reason, first match wins:
    1. the USB stick ALP-OS started from;
    2. in use right now (something on it is mounted);
    3. no card or medium inserted (size 0);
    4. read-only (for example an SD card with its lock switch on);
    5. holds an operating system (see (b));
    6. part of a disk group another system uses (RAID, LVM, ZFS, Windows
       Storage Spaces or dynamic disks, Apple RAID);
    7. already holds an ALP-OS archive (partition label `alp-data`;
       opening an existing archive is a later version; never erased);
    8. holds encrypted data ALP-OS cannot look inside (LUKS);
    9. too small (shows the size and the size needed);
    10. a USB or removable disk while the start stick could not be found
        (fail closed, as Live does since review 0.2.5).
- Reasons have a stable key (`holds_windows`, `boot_stick`, ...) for the
  translation files (spec 2.2) and an English fallback text.

## (b) Operating-system detection (greyed out, never selectable in 0.2.8)

Evidence comes from GPT partition type GUIDs, MBR type bytes and flags,
partition labels and file system names (`FSTYPE`). Any one is enough.

| Finding | Evidence |
|---|---|
| ALP-OS system | partition label `alp-state`, or a root partition labelled `alp-os_*` (disk-layout contract) |
| Windows | Microsoft reserved `E3C9E316-0B5C-4DB8-817D-F92DF00215AE`, Windows recovery `DE94BBA4-06D1-4D40-A16A-BFD50179D6AC`, fs `BitLocker` or `ReFS`; MBR `0x27`; NTFS on a disk that also has an EFI or Microsoft reserved partition; NTFS with the MBR boot flag `0x80` |
| macOS | APFS `7C3457EF-0000-11AA-AA11-00306543ECAC`, HFS+ `48465300-0000-11AA-AA11-00306543ECAC`, Apple boot `426F6F74-...`, Apple Core storage `53746F72-...`, Apple Silicon boot/recovery; fs `apfs`, `hfsplus`, `cs_fvault2`; MBR `0xab`, `0xaf` |
| Linux | root, `/usr` and their verity types for x86, x86-64, ARM, ARM-64 and RISC-V-64 (from the libfdisk table), Linux extended boot `BC13C2FF-...`, swap `0657FD6D-...`, home, server data, variable data, temporary data, user home; fs `swap`/`swsuspend`; BIOS boot `21686148-6449-6E6F-744E-656564454649`; MBR `0x82`, or `0x83` with the boot flag |
| ChromeOS, BSD, Solaris, other systems | their kernel/root/boot types from the libfdisk table (ChromeOS kernel/root, FreeBSD/NetBSD/OpenBSD/MidnightBSD/DragonFly, Solaris, Haiku, QNX, ...) |
| Unknown system | EFI system partition `C12A7328-F81F-11D2-BA4B-00A0C93EC93B` or MBR `0xef` with nothing more specific; any other MBR partition with the boot flag; `iso9660`/`udf` (a start stick or disc image of another system) |

Rules and limits:

- **Any ESP counts as "holds a system".** The ADR says "ESP with a boot
  loader"; looking for the loader means mounting the ESP. 0.2.8 does not
  mount anything, so an ESP alone is enough (fails safe: an empty ESP on an
  otherwise blank disk is greyed out too). A later version may mount it
  read-only to look for `EFI/*/*.efi`.
- **Known gap:** a Linux root on a plain "Linux filesystem" partition with
  its boot partition on another disk (or a legacy MBR install without the
  boot flag) looks like a data disk. It is then shown as *holds files* and
  needs the strong confirmation; it is not silently erased. Closing the
  gap means mounting read-only and looking for `/etc/os-release` (later).
- A plain NTFS/exFAT/FAT USB disk with no ESP/MSR/boot flag is a data disk
  (*holds files*), not Windows.
- Also counted as a system: fs `erofs`, `squashfs`, `DM_verity_hash`
  (read-only system images, Linux), and a FAT partition labelled `boot`,
  `bootfs`, `system-boot` or `EFI` (for example a Raspberry Pi card, which
  uses MBR without a boot flag).
- All 71 GUIDs in the code were checked by a script against the libfdisk
  2.39.3 table (names and values); the MBR bytes against its `dos` table.
- **The start stick is never offered:** the caller passes the kernel name
  of the disk ALP-OS runs from (`alp_hw::inspect` follows the root file
  system through dm-verity to its disk, as Live does). As a second guard,
  any disk with a mounted partition or holder is refused as "in use". If
  the start disk was not found, every USB or removable disk is refused.
- The verdict is computed again right before anything is written, and the
  write is refused if the disk, its size or its partitions changed since the
  user confirmed (spec block 7: never touch an unconfirmed disk;
  `alp_hw::safety::check_member` runs again in `alp-storage`).

## (c) Two paths

1. **Install on this computer.** The system goes on one internal disk
   (not USB, not removable). One disk: system plus `alp-data` on it
   (>= 64 GB; protection `dup`). More disks: system on the smallest
   suitable internal disk, `alp-data` partitions on the chosen data disks
   (`image/install-layout/data-disk/`); the system disk does not join the
   pool unless it is the only disk. Then remove the stick and restart.
2. **Keep running from the USB stick.** Nothing is installed; the stick
   stays the system disk and the chosen data disks (internal or USB) get an
   `alp-data` partition each. **Open (stream A):** the stick needs a state
   partition and updates in place (ADR 0026 layout); confirm this layout is
   what the 0.2.8 stick image has.

Both paths show the same disk list and the same confirm step (typed word or
press-and-hold, spec block 7), naming every disk that will be erased and
what is on it now.

## (d) Pool plan

- One data disk: Btrfs `dup` for data and metadata; the screen shows half
  the capacity and says it protects against damaged files, not against a
  dead disk. Two or more: `RAID1` for data and metadata. `RAID1c3` and
  `RAID10` only by explicit choice; `single` only by the advanced setting.
  RAID5/6 cannot be expressed (`alp_hw::RaidProfile` has no such variant).
- Usable capacity, RAID1 with different sizes: `min(total / 2, total -
  largest)`; dup: `size / 2` (minus metadata overhead; **VERIFY** against
  `btrfs filesystem usage` on the trixie btrfs-progs in the VM test).
- Members by GPT partition UUID (`PoolMember::ExistingPartition`), one LUKS2
  container per disk, all with the pool key (block 4, unchanged).
- **Room for the later "local backup disk" role:** a backup disk is never a
  pool member. It gets its own partition label (proposed `alp-backup`), its
  own LUKS2 container and its own Btrfs file system that receives read-only
  snapshots of `@archive` (local `btrfs send | btrfs receive`). The pool,
  its members and its subvolumes stay as they are; adding the role adds a
  label and a job, not a layout change. The disk list already reports such
  a disk as "holds an ALP-OS archive" and never erases it. Adding the label
  is a contract change to `disk-layout.md` when it comes. **Owner note:**
  spec block 4 lists "send/receive between nodes" as out of scope; local
  send/receive to a disk in the same box is a different thing, but should
  be confirmed then.

## (e) Built for tens of terabytes

- All sizes are `u64` bytes; display in decimal TB. Tests use 20 TB disks
  and a 6-disk RAID1 capacity case.
- Always GPT (MBR cannot address more than 2 TiB). 4K-sector disks: repart
  handles alignment (**VERIFY** in the 2-disk VM test with a 4Kn virtual
  disk, `logical_block_size=4096`).
- Discovery reads no file data and does not wake sleeping disks except the
  targeted `blkid -p`; the list is small whatever the archive size.
- Scrub and balance on tens of TB take many hours: throttled, resumable
  across reboots, shown with an estimate (block 4). First pool creation does
  not pre-write the disks (no full-disk wipe; LUKS2 `--integrity` is not
  used, so no initial pass) — **VERIFY** in stream B's plan.

## Tests

- Unit tests (this step, `cargo test -p alp-hw`): fixtures for a blank
  disk, a Windows disk (ESP + MSR + NTFS + WinRE), a BitLocker disk, a Linux
  disk (ESP + root + swap), a macOS disk, the boot USB stick (mounted), an
  SD card, an SD reader with no card, a disk with one data partition, an
  ALP-OS archive disk, LVM/RAID members, a LUKS disk, an MBR Windows disk,
  loop/zram skipped, the old all-strings lsblk form, start stick unknown,
  size limits, 20 TB disks.
- Later (installer library): scripted installs on 1 and 2 virtual disks;
  a VM with a fake Windows disk (GPT with ESP + MSR, made by `sfdisk` on a
  virtual disk in the harness) proves it is greyed out and untouched (disk
  hash before = after); legacy BIOS VM shows `ALP-INST-001`.

## Open questions for the owner

1. **Disks that hold files but no system** (for example a USB disk with
   photos on NTFS): offer them, erased after a strong confirmation that
   names what is on them (this plan), or grey them out in 0.2.8 too?
   Recommendation: offer them, with the file system label shown and the
   strong confirmation; greying them out would block most second-hand
   data disks.
2. **Data disk minimum size:** the hardware profile has none. Proposal:
   32 GB (same as a system disk). Adding it to the profile is a contract
   change.
3. **Encrypted (LUKS) disks** are refused in 0.2.8 because ALP-OS cannot
   tell whether they hold a system. Confirm.
