# 0.2.8: reopen an archive with the recovery code after losing the system disk

Owner decision 2026-11-25: in 0.2.8. Until now the installer greys out every
disk with an `alp-data` partition ("Already holds an ALP-OS archive") and
only a new pool can be made.

## User flow

1. First setup on the stick, place step: the install page lists the old
   archive disks as **"ALP-OS archive: can be opened again"** instead of
   greyed out. The user picks the new system disk and ticks the archive
   disks to reopen (never erased, no strong confirmation needed, nothing is
   written to them by the installer).
2. Install writes the system disk only (layout `system`, no `alp-data` on
   it) and a seed with `reopen = true` and the chosen `alp-data`
   partitions as members. Restart from the installed disk.
3. First start: password (index), then **"Type your 15 recovery words"**
   (and the serious-encryption passphrase if one was set) instead of
   "Preparing your disks". A wrong code says so and nothing changes.
4. The archive opens; photos, albums and the gallery come back (Immich data
   is on the pool, `@immich`). Then a new recovery code is NOT needed: the
   old words keep working. Phones pair again (the old index is gone).

## Design

- **Installer / alp-hw blockdev**: an `alp-data` disk whose partitions are
  all `alp-data` LUKS members (label `ALPDATA`, pool LUKS label) gets the
  verdict `Usable { roles: [Reopen] }`. Any other content keeps the old
  "Already holds an ALP-OS archive" reason. `Reopen` disks never get a
  `systemd-repart` step and are never named in an erase list. The confirm
  token covers only erased disks; reopen disks are checked again at first
  start by `seed_check` (same disks, same partitions).
- **Seed** (`firstboot-seed.md`): optional `reopen = true` (default false,
  `format_version` stays 1: old seeds read the same). For reopen the
  members are the existing `alp-data` partitions; `data_profile` /
  `metadata_profile` are computed as for a new pool (so `seed_check` and the
  plan digest work unchanged); the record takes the real profile from
  btrfs after opening.
- **alpd**: `state.pool` = `"reopen"` while such a seed waits.
  `POST live/archive/reopen-pool {words, passphrase?}` (console session,
  Origin) starts job `archive.reopen`. Wrong code: the job fails with error key
  `recovery.wrong` (`ALP-STO-126`, counts as a failed try), nothing written.
- **alp-storage** `pool::reopen(members, secret, new_key)`, per member:
  1. `cryptsetup open --test-passphrase --key-slot=1|2` with the secret
     (stdin): the words must open a recovery slot of every member, else
     wrong code, stop before any change (words that opened only slot 0
     would leave no way in after step 3).
  2. If slot 0 is in use and opens with the new pool key: skip (resume).
     An empty slot 0 answers "No usable keyslot", which means "not yet".
  3. `luksKillSlot --batch-mode dev 0` (only if slot 0 is in use), then
     `luksAddKey --new-key-slot=0` authorised by the secret. The recovery
     slots stay, so a power cut between the two steps leaves the member
     openable by the words and the next try finishes it.
  New key input: the existing passphrase (secret, hex, one line) comes on
  stdin; the new 64-byte binary key cannot follow on stdin (a newline byte
  would end it), so it is passed as `--new-keyfile` pointing at a 0600 file
  in `/run/alp` (tmpfs, never on disk), removed right after. Checked against the cryptsetup 2.7.5
  source: `--new-keyfile` with `--new-keyfile-size=64`.
- Then the normal `pool::open` with the new key, `btrfs filesystem show`
  checks every member belongs to one filesystem (same fs UUID), the record
  is written from what is found (fs UUID, members, data profile from
  `btrfs filesystem df`, screen names), the recovery state is "set"
  (slots 1/2 as they are), and the seed goes.
- **Screen** (design thread): setup step `Words` when `pool == "reopen"`;
  the install page shows the Reopen role.

## Tests

- Unit: blockdev verdict (reopen-able archive, mixed disk stays greyed);
  seed round trip with `reopen`; installer runs no repart on reopen disks;
  storage `reopen` command order, secrets only on stdin, wrong code changes
  nothing, resume after a cut between kill and add.
- VM: T-INST-02 part 5: a new blank system disk plus the same two data
  disks; install with reopen; first start with the words; the 200 MB test
  file's SHA-256 matches part 2; `@immich` mounted; a wrong code first is
  refused and changes nothing.

## Risks

- Immich's own admin account lives in its database on the pool; the new
  index does not know its password. Reuse the reset path
  (`immich-admin reset-admin-password`) on reopen. **VERIFY** in the VM test.
- A pool with a member missing at reopen: refused in 0.2.8 (all members
  must be present); degraded reopen later.
- Both recovery slots in use (the old system was halfway through changing
  the code): nothing records which one is current, so making a new code
  after the reopen is refused. Settling it at reopen (keep the slot the
  typed words open) is a follow-up.
- Only some of an archive's disks chosen: the members get the new key,
  then the open fails ("not one whole archive"). Safe (the words still
  open them), but the message is vague; counting members before the
  rekey is a follow-up.
- `create-pool` refuses a reopen seed (`archive.reopen_needed`), so a new
  pool is never made on an old archive's disks.
